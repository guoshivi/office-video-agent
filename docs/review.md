# 审核台：机器预检 + 人工拍板

出片和发布之间必须站一个人。不是不信任模型，而是这条链路上的错误代价不对称：
写错面积、串了楼栋、文案里漏了微信号，发出去是真实的经营损失，删帖和道歉都补不回来。

审核台要解决的就是这件事——**让人一分钟内看完一条片子，并且没法糊里糊涂地放过问题。**

## 一、为什么不是「出片直接发」

先说清楚不做全自动的理由，免得以后有人来问为什么多这一步：

1. **事实类错误只能靠比对。** 模型写文案时可能把「一百二十平」说成「一百五十平」，
   口语顺得听不出来，但客户一到现场就露馅。这种事机器能做的是**比对**（文案 vs 房源库），
   判断「这个差异是不是可接受」还得人来做。
2. **平台侧错误代价不可逆。** 小红书标题硬顶 20 字、正文 1000 字，超了直接截断；
   引流词会限流封号。这些是发布前一刻才能确认的事。
3. **中介号不是矩阵号。** 一个号养起来很贵，发废几条内容就掉权重。宁可少发。

## 二、预检：机器能定的部分

`app/review/precheck.py`，纯函数，不碰数据库、不碰网络，输入一条任务，输出一份报告。

每条结论是三级之一：

| 级别 | 含义 | 通过时要不要额外确认 |
|---|---|---|
| `blocking` | 明确错了，发出去会出事 | 要，且必须显式 `confirm_risky` |
| `warn` | 可疑或信息缺失，人工看着办 | 不用，但会显示在审核页上 |
| `ok` | 已核对通过 | — |

一共九组检查：

| id | 检查 | 级别规则 |
|---|---|---|
| `script` | 口播文案非空 | 空 → blocking |
| `video` | 成片文件存在 | 不存在 / 空路径 → blocking |
| `media` | ffprobe 体检 | 读不出参数 → warn（不冒充 blocking） |
| `audio` | 有没有音轨 | 没有 → blocking（配音没进去） |
| `aspect` | 画幅 | 横版发竖版平台 → warn |
| `duration` | 时长 | <15s 或 >90s → warn |
| `area` | 面积一致性 | 文案里的平数 vs 房源库，容差 8 平，超了 → blocking |
| `rent` | 租金一致性 | 差 5% 以上 → blocking |
| `identity` | 房源一致性 | 文案里出现了**别的楼栋**（串房）→ blocking |
| `compliance` | 引流词 / 绝对化用语 | 微信、QQ、手机号、加我 → blocking；私信我、最低价、保证 → warn |
| `hygiene` | 对外措辞 | 内部用语漏进成片 → blocking |
| `duplicate` | 重复发布 | 这套房源已经发过 → warn |

两个值得单独说的：

**`hygiene`（对外措辞）是真实事故催出来的。** 早期两条成片的口播里带着
「租金和物业费口径请以最新房源确认为准」——这是写给内部人看的提醒，
被配音念出来就变成了对客户说「我们的价格不确定」。所以有了这份黑名单：

```
口径 / 请以最新 / 以实际为准 / 内部 / 备注 / 待确认 / 需确认 / 仅供参考 / 不对外 / AI 生成
```

**`identity`（串房）** 是中介场景里最丢人的错误：讲 1201 的房子，文案里冒出隔壁楼的名字。
做法是把文案里出现的楼栋名跟房源库里**其它**房源的楼栋名做差集，命中就是串了。

### 面积/租金为什么容错

中文口播里「一百二十平」和「120㎡」是同一件事，「一万二」和「12000元/月」也是。
`cn_to_int()` 负责这层转换，并且专门处理了省略说法（「一万二」= 12000，不是 10000）。
金额比对留 5% 容差，因为中介口头常说「一万二左右」。

## 三、出片前就摘掉，别等审

`hygiene` 那条规则如果只在审核时生效，会有一个很贵的问题：
出错的是**已经渲染好的成片**，修一次要重跑十几分钟，当天大概率发不出去。

所以同一个词表（`app/hygiene.py`）在两个时机各用一次：

| 时机 | 位置 | 动作 |
|---|---|---|
| 出片前 | `workbench_client._render_once()` | 送进配音之前把带内部用语的整句摘掉，并记一条 warning |
| 导出任务包时 | `services.export_workbench_package()` | 写 `script.txt` 前摘一次，warning 写进 manifest |
| 审核时 | `precheck._check_hygiene()` | 成片对应的文案里还有，就 blocking |

只摘整句，不改写剩下的内容——改写会把「一百二十平」这种事实也一起动了。
如果整段都带内部用语（摘完什么都不剩），原样返回：
让工作台出一条有瑕疵的片子（审核台还会拦），也好过把空文案送进配音直接报错。

真实效果：

```
原文：正在找办公室的朋友，今天看一套位于F区、F14的房源。面积信息为120平，
      格局为店面，朝向向南。租金和物业费口径请以最新房源确认为准。欢迎私信咨询。
清理：正在找办公室的朋友，今天看一套位于F区、F14的房源。面积信息为120平，
      格局为店面，朝向向南。欢迎私信咨询。
```

## 四、队列与状态机

`app/review/store.py` 只负责存取，`app/review/service.py` 负责编排。
这条分界很硬：**存储层不许知道「通过之后要不要发」**，否则换发布实现要动数据库代码。

```
pending ──approve──> approved ──publish_now──> published
   │                    ▲
   ├──reject──> rejected│
   └──skip────> skipped │
                        │
   多维表格裁决 ─────────┘（只在本地仍为 pending 时生效）
```

关键规则：

- **入队是幂等的。** `store.create()` 同一个 task 调两次返回同一个 id。
  出片流程里调一次、`refresh_queue()` 补历史时再调一次，不会出现两条。
- **没预检不许通过。** `approve()` 发现 `level == "unknown"` 会先补跑一次预检再判断，
  否则「审核台的第一次点击」等于绕过整个审核台。
- **blocking 要显式越过。** 误报是存在的（比如面积口径人工确认过），
  但越过必须带 `confirm_risky=True`，并且会在 note 里留下「预检有风险，人工确认后通过」。
- **驳回必须写原因。** 不写就没有 `note`，出片的人不知道该改什么，
  这条片子下次还会以同样的样子回来。
- **不硬插在出片流程里。** `refresh_queue()` 用查询补齐「已出片但未入队」的任务，
  而不是在出片线程里加一步。理由是出片线程已经很忙，而且历史上已经出好的片子也要能补进来。

## 五、多维表格桥接

`app/review/bitable_bridge.py`。**本地 SQLite 始终是权威，表格只是它的一个视图。**

为什么要两边都能审：朋友在外面用手机审、在电脑上用 WebUI 审，两边都要能操作同一条队列。

两个方向：

- `push_item()` / `push_all()`：本地队列 → 表格一行，以「任务编号」为键，有则更新无则新建
- `pull_decisions()`：表格里「审核状态」被改成通过/驳回 → 回写本地

几个刻意的决定：

1. **轮询而不是 webhook。** 飞书多维表格的自动化流程能发 HTTP 请求，
   但需要有公网可达地址，而朋友那台机器在内网。30 秒的延迟对「审完再发」完全够用。
2. **只拉不改已裁决的。** 本地已经是 `approved` / `rejected` 的记录跳过，
   否则人在 WebUI 上刚改完，会被表格里的旧值盖回去。
3. **表格驳回没填原因也能落地。** 用「多维表格驳回」占位。
   宁可留一条信息不全的记录，也不要让流程卡在「没原因所以拒不动」上。
4. **没凭据就整体静默失效。** 不是错误，`available() == False`，审核台照常能用。

表里需要的列（缺列只记日志、不抛异常，因为一张表的字段改名不该卡住出片）：

```
任务编号 / 房源 / 面积 / 口播文案 / 预检结论 / 审核状态 / 审核人 / 驳回原因
```

开关是 `REVIEW_BITABLE_SYNC=1`，同时需要 `FEISHU_BASE_APP_TOKEN` 和 `FEISHU_TASK_TABLE_ID`。
写表走 REST + `tenant_access_token`，**不订阅事件**，所以不会和 WorkBuddy 的飞书长连接抢消息。

## 六、怎么用

### WebUI

审核页（左侧第二项）是左右分栏：左边队列卡片带首帧缩略图，右边是视频、预检清单、决策按钮。

键盘流（默认焦点在队列上）：

| 键 | 动作 |
|---|---|
| `J` / `K` | 下一条 / 上一条 |
| `A` | 通过 |
| `R` | 驳回（弹出原因输入） |
| `G` | 跳到发布面板 |

预检有 blocking 时，「通过」按钮会自动变成「强行通过」并变红，点下去要再确认一次。

### 命令行

```bash
./.venv/Scripts/python.exe tools/ova.py review                 # 看待审队列
./.venv/Scripts/python.exe tools/ova.py check V20261101-ABCDE  # 重跑预检，看逐项结论
./.venv/Scripts/python.exe tools/ova.py approve V20261101-ABCDE
./.venv/Scripts/python.exe tools/ova.py approve V20261101-ABCDE --force   # 越过 blocking
./.venv/Scripts/python.exe tools/ova.py reject V20261101-ABCDE --note "画面太暗"
./.venv/Scripts/python.exe tools/ova.py publish V20261101-ABCDE --set xiaohongshu
```

中文别名可用：`审核` / `预检` / `通过` / `驳回` / `发布`。

### API

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/review/items?status=&refresh=` | 队列；`refresh=1` 会补入队并补跑预检 |
| GET | `/api/review/counts` | 各状态条数 |
| GET | `/api/review/{task_id}` | 单条详情（含分组后的预检结论） |
| POST | `/api/review/{task_id}/precheck` | 重跑预检 |
| POST | `/api/review/{task_id}/approve` | `{reviewer, note, confirm_risky, platforms}` |
| POST | `/api/review/{task_id}/reject` | `{reviewer, note}`，note 必填 |
| POST | `/api/review/{task_id}/skip` | `{note}` |
| GET | `/api/review/bitable/status` | 表格接入状态 |
| POST | `/api/review/bitable/push` | 推送队列（`?task_id=` 推单条） |
| POST | `/api/review/bitable/pull` | 拉一次人工裁决 |

## 七、和发布的关系

审核通过后发不发，由 `PUBLISH_AUTO_AFTER_REVIEW` 决定：

- `0`（默认）：通过只是通过，去发布面板手动发。**建议一直保持 0**，直到你敢让机器连夜发。
- `1`：通过即调 `publish_task()`，走发布层那套规则校验和频率控制。

无论哪种，`publish_now()` 失败都不会把状态改回 `pending`——它保持 `approved`。
理由是「审核结论」和「发布结果」是两件事，混在一起会让人分不清
「这条没被批准」和「这条批准了但小红书那边挂了」。

具体的平台行为、踩过的坑见 [publish.md](publish.md)。

## 八、已知边界

- **预检不懂语义。** 它只会比数字和查词表。「这套采光特别好」是不是吹牛，它不知道。
- **串房检测依赖房源库里的楼栋名。** 文案里用了简称（「深港」而不是「深港大厦」）可能漏检。
  楼栋名字段越完整，这一项越准。
- **重复发布只查本地记录。** 如果同一个房源在 app 之外被人发过，这里看不出来。
- **多维表格的字段类型没适配。** 现在按纯文本写。如果表里把「审核状态」设成单选，
  飞书可能会拒掉不在选项里的值——真遇到了就把选项补齐，或者把这一列改成文本。
