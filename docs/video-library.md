# 00 拆解：把一条爆款拆成能照着拍的模板

目的只有一个：**看完一条别人的爆款，知道自己该怎么拍**。

拆解不是"识别视频内容"，是把一条片子压成四样东西：

| 产出 | 谁算的 | 有什么用 |
| --- | --- | --- |
| 几个镜头、每个几秒 | ffmpeg 场景切点 | 决定你的拍摄节奏 |
| 每镜拍的是什么 | WorkBuddy 看拼图 | 决定你的镜头顺序 |
| 每句说了什么 | OCR（别人片子上的烧录字幕）/ 人工 | 决定你的文案骨架 |
| 每镜担什么角色 | 规则 + 复核 | 决定开头、卖点、收尾怎么排 |

## 一、两档能力，装了 OCR 就够

00 拆解不要求装任何模型。装得越多，拆得越细：

```
第 1 档  零依赖      只要能跑 ffmpeg 就能用：镜头数、每镜时长、切点位置
第 2 档  + OCR       能读出画面里烧录的字幕（剪映导出的片子基本都有）
```

每档都在 `data/templates/<id>/checklist.json` 里写明。拆到哪一档、缺什么，
`warnings` 里会直接写人话，不会只弹一个报错。

装法：

```bat
REM 第 2 档：读字幕
.venv\Scripts\python.exe -m pip install --no-deps -r requirements-analyze.txt
```

### 为什么不做语音识别

我们的生产路径是 **空镜素材 + 脚本文案 + TTS 配音**——自己拍的片子里
本来就没有真人说话，旁白是后期配的。拆解要回答的是「画面怎么排」，
不是「嘴说了什么」。

实测一条 10.57 秒的空房带看片：音轨平均 **-43.9dB**（正常说话在 -25 以上），
逐秒电平全程 -42~-48，一个字都没有。这种片子装多大的语音模型都是空转。

代码里 `transcribe()` 还留着，遇到「别人拍的、没有字幕、但有真人说话」
的爆款时可以用（`tools/fetch_asr_model.py` 下模型）。但这种片子是低频，
真遇上抽 8 帧交给 WorkBuddy 看更快，不值得为它装 1.5GB。

## 二、流程

```
上传视频 / 贴链接
      ↓  自动：切点 → 抽帧 → OCR → 合成结构
   spec（说话人是谁不重要，结构先出来）
      ↓  POST /api/templates/{id}/pack
   grid.jpg（镜头拼图）+ checklist.json（待填清单）
      ↓  WorkBuddy 看图，填 subject / role / why，纠台词
   PUT /api/templates/{id}/review
      ↓
   可直接套到任务的模板
```

**为什么要中间这一步"交给 WorkBuddy 看"**：本地没有任何模型能判断
"这镜拍的是老板间还是会议室"，embedding 也不行——它对同类画面的相似度
在 0.81~0.87，只够粗分。而看一张拼图就能判断，还能顺手纠正 OCR 读错的字。
这一步不联网、不装模型，是把视频压成一张图交给人看。

## 三、OCR 的三个坑（都已处理，改动时别踩回去）

**坑 1：画面上的字不都是字幕。**
一条 25 秒的产品片，OCR 在画面下方读出 87 段文字，其中 85 段是包装上的字。
按"在画面下方"分字幕，等于把包装说明当台词。

现在的判据是**时间连续性**：口播字幕是一条不断的流，每 1~2 秒换一句、
从片头铺到片尾，中间不会有大段空白；包装、门头、易拉宝上的字只在某个
镜头出现一次，前后都是空白。所以按 y 分桶后，只保留"段数够多、最大空隙
小于 2.5 秒、位置在下半屏"的那一桶。

试过但**不成立**的两个判据，别再改回去：

- 按重复度挑 → 会选中包装上反复出现的那行字；
- 按文本多变挑 → 会选中背面特写里被读花的说明字。

**坑 2：一句话会被读成好几段。**
OCR 每秒抽 1.2 帧，一句字幕连着出现两三帧，每帧读出来还略有出入
（「怎么分辨」/「怎么分瓣」）。只按文本相等合并会剩一堆碎片；
只按时间间隙合并更糟——抽帧间隔是 0.83 秒，同句和相邻句一样长，
一路并下去整条片子只剩两句。现在的做法是**时间间隙 + 文本相似度双条件**。

**坑 3：镜头和台词是两套时间轴。**
一条 25 秒的片子可能只有 8 个镜头，却有 20 多句台词。
拼图必须按**镜头**抽帧（`scene_spans`），按台词抽会抽出同一镜头的十几个
瞬间，等于没拼。清单里每句都标了 `scene` 号，回填时按镜头下发角色。

## 四、复核结果怎么填

`PUT /api/templates/{id}/review` 分两层，因为看图得到的信息本来就是两层：

```json
{
  "summary": "先立焦虑，再用包装/条码/产地三重证据证明正品，最后报价收口",
  "scenes": [
    {"scene": 1, "subject": "手持产品特写", "role": "hook", "why": "先抛假货多制造焦虑"},
    {"scene": 8, "subject": "箱内特写", "role": "cta", "why": "只负责指路左下角"}
  ],
  "shots": [
    {"index": 4, "line": "怎么分辨真假呢"},
    {"index": 8, "drop": true}
  ]
}
```

- `scenes` 按镜头给语义，同一镜里所有台词都继承这个角色；
- `shots` 按句子纠台词，`drop` 删掉 OCR 读出来的噪声句；
- 没填的字段保留原值，漏填不会把已经拆出来的东西清掉。

**镜头语义单独存一份**（`spec.scenes`），不能只挂在台词上：
最后一个收尾镜常常只有 1.3 秒、一句话都没有，角色跟着台词走就会整镜消失，
结构占比里就缺了 cta 那 5%。

## 五、套到任务上

```bash
POST /api/tasks/{task_id}/apply-template   {"template_id": "..."}
```

- 配了 `ARK_API_KEY`：走云端模型，按模板结构重写文案；
- **没配**：走本地句式库（`copywriting.fallback_storyboard`），
  按模板的镜数和角色路由已有句式，只填房源字段，不编事实。
  返回里的 `engine` 会写 `local`，能看出走的是哪条路。

所以"拆完能不能用"不再取决于有没有付费 key。

## 六、结构占比按镜头算，不按台词算

这一条很容易写错。台词只在有人说话时才有时间，拿它当分母会算出一条片子
只有一半时长；而"钩子占开头几秒"问的是镜头。所以 `shares` 用
`scene_spans` 的镜头时长累加，合计必须约等于整片时长——对不上就是算错了。

## 七、一镜到底的片子（空镜素材最常见）

中介自己拍的素材常常是**一条连续走位**：从门口推进去，边走边转，10 秒不剪。
这类片子 `scene_cuts` 返回 **0 个切点**，整片会被当成 1 个镜头，
拆出来是「1 个镜头 10.6 秒」——对拍摄指导没有任何用处。

处理方式与原因：

- **按时间等分**（`count = clamp(round(时长/2.5), 2, 8)`），每段标 `synthetic: true`，
  并在 `warnings` 里明说「这些边界是等分的，必须人工划段」，不许装成真镜头；
- **不试图自动找边界**。试过用 HSV 直方图帧差找局部峰：一条 10 秒片切出
  21 个峰，全落在镜头扫过窗户的瞬间（画面剧变是运镜造成的，不是换空间）。
  一镜里的空间段落只能靠**看画面**判断，脚本猜不准；
- 拼图必须用这些等分段落抽帧（`reviewpack.spec_spans`），否则只切出 1 格；
- **拼图列数跟着镜头数走**（`_grid_columns`）。固定 4 列时，5 段会排成
  「4 格 + 1 格 + 3 块白」，图片凭空高一截，详情页一屏全是拼图，
  改角色的下拉要往下滚一屏半。现在 5~6 段用 3 列（3+2，只空一格）、
  4 段用 2×2；
- 有台词的片子 `shots` 是**句子级**（25 秒可能 17 句 / 8 镜），
  绝对不能当镜头边界用——这条判断写在 `spec_spans` 里。

### 套用时补收尾镜

空镜素材几乎都没有 CTA（拍完就走）。`_compact_spec` 检测到模板里没有 `cta`
时会补一镜，标 `added: true`。**不能像以前那样把收尾语塞进最后一镜**——
最后一镜可能是"长条工位桌"，配一句"感兴趣的老板过来看看"是错位。

### 同一卖点重复时，宁可重说也不许编

`_ROLE_TO_TOPIC` 里认不出的角色以前全落到 `"light"`（默认值写错了），
导致一条片子四句里三句都在讲采光。修掉之后又走到另一个极端：
只要某个卖点用过一次，就从固定池里换下一个——**换成了画面里根本不存在的东西**。

实测踩到：一条 13 秒的门店横移，第 2 镜和第 4 镜拍的都是家具（茶桌、靠窗工位）。
第 2 句按 `furn` 写成「工桌工椅全套配齐」没问题，第 4 镜因为 `furn` 用过了，
被轮换池塞了一句**「独立老板间，谈单不吵」**——画面里是打印机和文件，
客户一句"老板间在哪"就把中介问住了。

现在的规则：

1. 卖点重复，但画面（`subject`）里确实还有这个卖点 → **保持原卖点**，
   由句库换一句不同角度的（`pick()` 内部按游标轮转 + 去重）；
2. 卖点重复，而且 `subject` 里压根没提这个卖点（骨架猜错了）→
   只换成 `subject` 里**写得出来的**卖点（`_TOPIC_HINTS` 词表匹配）；
3. 一个都对不上 → 保持原卖点。**编错比重复严重。**

配套改的是 `_LINE_BANK["furn"]` 的排序。原来四句里前两句几乎同义
（"全套配齐""拎包就能办公"），连着取正好撞上；现在按
齐全 / 省钱 / 归属 / 状态四个角度排开，连着说两句也不撞。

## 八、拆解引擎：本地优先，云端可选

`analyze()` 默认走**本地引擎**（`STYLE_ENGINE` 未设或为 `local`）：
ffmpeg 找切点 + OCR 读字幕 + 一镜到底等分，跟拼图复核用的是同一份 spec。

方舟视频理解留成可选增强（`STYLE_ENGINE=ark` 且有 `ARK_API_KEY`），不设默认，因为：

- 它要先把整条片子传上去做预处理（512MB 上限、0.5fps 抽帧），又慢又贵；
- 它自己判镜头，和拼图复核、结构占比用的那套时间轴**对不上**；
- 最要紧的是——**拆解是本地能力，不该被云端 key 挡住**。

这条最早是断的：`analyze()` 整条走方舟，没 key 直接 `failed`，
而"没配 key"恰恰是最常见的使用环境，"上传 → 看拼图 → 复核"第一步就断了，
后面拼图、占比、套用全都没机会发生。`/api/templates` 返回里
`configured` 现在只表示**云端增强**可不可用，`engine` 表示这次用哪个引擎拆。
